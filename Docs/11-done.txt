# The done list. Docs/11 §10 is about this file; this file is the list.
#
# Authoritative. `make status` reads it, counts it against the backlog in Docs/09, and
# cross-checks it against what commit subjects claim. A ticket belongs here only when its
# *Done when* line in Docs/09 is demonstrable.
#
# Docs/11 §4 lists the partly-finished tickets, and they are NOT all absent from this list.
# Every ticket §4 names is here. SHIP-151 is the newest of them: it landed, it is named by a
# commit subject, and one clause of its *Done when* — the search by name — has no column in the
# schema to search. SHIP-149 was such a row until SHIP-150 built its write helper, SHIP-65 until
# SHIP-67 closed it, and SHIP-134 until its publisher landed, which is how this shape is meant to
# end. Do not "tidy" any of them out: `make status` exits 1 when git shows a ticket this file
# does not declare, so removing one breaks the build rather than making it more honest.
# Docs/11 §10 carries the full reasoning.
#
# This paragraph was itself duplicated and self-contradictory until the wave-4 reconciliation —
# a merge=union artefact, and the reason the attribute is confined to a file whose content lines
# are independent tokens. Prose in a union-merged file is the one thing to keep short.
#
# Add a ticket in the same change that finishes it, in the same commit as the Docs/11 §3 entry
# that says what it built.
#
# # Why this is a file of its own, and not a fenced block in Docs/11
#
# It is `merge=union` in .gitattributes, which no Markdown document could be. Every track in a
# wave appends to the done list, so the last merge of a wave always conflicted here — twice in
# wave 2, and both resolutions were unions. A union is safe for *this* content and for very
# little else: the lines are independent tokens with no syntax to break, a union is always a
# superset, and `make status` **fails** when the list claims a ticket git has never seen. So a
# bad union is caught by a check rather than passing quietly. That is the same argument
# .gitattributes already makes for routes_golden.txt.
#
# Docs/11 §3 is prose and is deliberately *not* union-merged: a union there interleaves two
# narratives, which is worse than a conflict because it is harder to notice. Since a git
# attribute applies to a whole file, the list had to move out of the document for the two to be
# treated differently. That move is the whole of the decision (SHIP-15e).
#
# # One ticket per line, and that part is load-bearing
#
# merge=union resolves line by line. The list used to be grouped several tickets to a line, and
# two tracks appending to the same line would still have conflicted — the union would have had
# nothing to keep both of.
#
# # And the order does matter, which is a correction (SHIP-15t)
#
# This paragraph used to end "Order does not matter: the reader sorts." That is true of
# `make status`, which sorts before it counts, and false of every human reading the file — and it
# is the sentence that let the same defect happen twice. A union appends in *merge* order while
# this list is written in *build* order, so a wave's merge lands its tickets wherever the merge
# put them. `23618e5` is titled "restore the sorted position a union broke" and moved SHIP-15g
# back from below the M7 group; wave 8 then put SHIP-120 and SHIP-120a between SHIP-112 and
# SHIP-114 the same way, and nothing caught it, because counting rows cannot see where they sit.
#
# **`make status` now checks the order** and fails on a third occurrence. The check is in
# `scripts/delivery-status.sh`; note that `sort -c` is the wrong instrument, exactly as it is for
# routes_golden.txt — the order here is by ticket number with letter suffixes
# (SHIP-120, SHIP-120a, SHIP-121), which is not the lexicographic order of the lines.
#
